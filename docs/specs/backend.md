# [Backend] 여행 앱 서버 API 스펙

## Problem Statement

친구들과 국내 여행을 가면 계획은 메신저 대화방에, 사진은 각자의 휴대폰에, 지출은 총무의 메모에 흩어진다. 여행 중 어디를 어떻게 다녔는지는 기억에만 남고, 공동 지출은 공동 품목·일부 인원 품목·개인 물품이 섞여 있어 총액을 인원수로 나누면 실제 부담과 어긋난다. 정산 후 지출이 고쳐지면 이미 오간 송금까지 고려해 다시 계산해야 한다.

앱(프론트엔드)이 이 문제를 풀려면, 여행·멤버·장소·일정 항목·사진·지출·송금을 한곳에서 권한에 맞게 저장하고, AI 결과를 검증하고, 잔액과 송금 제안을 정확히 계산해 주는 서버가 필요하다.

## Solution

FastAPI 서버 하나가 앱의 모든 데이터 요청을 받는다(ADR-0002). 앱은 Supabase Auth로 로그인만 직접 하고, 로그인 토큰을 붙여 서버를 호출한다. 서버는:

- 여행 하나를 그룹 하나로 다룬다(ADR-0001). 초대 코드로 멤버가 들어오고, 여행을 만든 멤버가 총무다.
- 플래너(일정 항목)와 앨범(사진)은 모든 멤버가 채우고, 지출과 송금은 총무만 다룬다.
- Gemini로 추천 일정과 지출 초안(영수증 분석)을 만들고, 카카오 로컬 API로 장소가 실제로 있는지 검증한다.
- 사진은 앱이 휴대폰 안에서 촬영 위치로 찾아 준 장소에 연결해 저장한다. 서버는 사람의 위치 좌표를 받거나 저장하지 않는다(ADR-0003).
- 확정된 지출과 송금으로 멤버별 결제액·부담액·잔액과 송금 제안을 계산하고, 지출이 바뀌면 재정산한다.
- 장소를 중심으로 일정 항목·사진·지출을 묶어 지도 화면에 필요한 데이터를 한 번에 내준다.

## User Stories

### 계정과 여행

1. 사용자로서, 로그인 토큰만으로 서버가 나를 식별하길 원한다, 그래야 앱에서 별도 인증 없이 내 여행을 불러올 수 있다.
2. 사용자로서, 내가 멤버인 여행 목록을 보고 싶다, 그래야 지난 여행과 다가올 여행을 고를 수 있다.
3. 사용자로서, 여행 이름·시작일·종료일을 정해 여행을 만들고 싶다, 그래야 친구들을 초대할 수 있다.
4. 여행을 만든 사용자로서, 자동으로 그 여행의 총무가 되길 원한다, 그래야 따로 권한 설정을 하지 않아도 된다.
5. 총무로서, 초대 코드를 발급받고 싶다, 그래야 친구들에게 공유할 수 있다.
6. 총무로서, 초대 코드를 재발급하고 싶다, 그래야 잘못 퍼진 코드를 무효로 만들 수 있다.
7. 사용자로서, 초대 코드를 입력해 여행의 멤버가 되고 싶다, 그래야 플래너와 앨범에 참여할 수 있다.
8. 사용자로서, 잘못되었거나 무효가 된 초대 코드에는 명확한 오류를 받고 싶다, 그래야 총무에게 새 코드를 요청할 수 있다.
9. 사용자로서, 이미 멤버인 여행의 코드를 다시 입력해도 중복 가입되지 않길 원한다.
10. 사용자로서, 멤버가 10명인 여행에는 들어갈 수 없다는 안내를 받고 싶다.
11. 총무로서, 여행 기간을 바꾸고 싶다, 그래야 일정 변경을 반영할 수 있다.
12. 총무로서, 일정 항목이 있는 날짜가 사라지도록 기간을 줄이려 하면 거절되길 원한다, 그래야 계획이 몰래 사라지지 않는다.
13. 멤버로서, 지출에 엮인 적이 없다면 여행에서 나가고 싶다.
14. 멤버로서, 결제자나 분담 대상으로 지정된 적이 있으면 나갈 수 없다는 이유를 듣고 싶다, 그래야 잔액이 깨지지 않는다.
15. 총무로서, 지출에 엮인 적 없는 멤버를 내보내고 싶다.
16. 총무로서, 여행에서 나갈 수 없다는 점이 서버에서 보장되길 원한다, 그래야 지출 관리자가 사라지지 않는다.
17. 총무로서, 여행을 통째로 삭제하고 싶다, 그래야 테스트용이나 취소된 여행을 정리할 수 있다.
18. 멤버로서, 내가 나가면 내가 올린 사진이 함께 지워지길 원한다.

### 장소와 플래너

19. 멤버로서, 키워드로 실제 장소를 검색하고 싶다, 그래야 일정 항목에 정확한 장소를 붙일 수 있다.
20. 멤버로서, 같은 곳을 두 번 일정에 넣어도 장소가 하나로 유지되길 원한다, 그래야 지도에서 핀이 겹치지 않는다.
21. 멤버로서, 날짜별로 일정 항목을 추가하고 싶다(시간, 장소, 메모, 예상 비용).
22. 멤버로서, 장소 없는 일정 항목("자유시간")도 만들고 싶다.
23. 멤버로서, 다른 멤버가 만든 일정 항목도 고치고 싶다, 그래야 함께 계획을 다듬을 수 있다.
24. 멤버로서, 내가 만든 일정 항목을 지우고 싶다.
25. 총무로서, 누가 만든 일정 항목이든 지우고 싶다.
26. 멤버로서, 하루 안에서 일정 항목의 순서를 바꾸고 싶다.
27. 멤버로서, 여행 기간 밖의 날짜에 일정 항목을 만들려 하면 거절되길 원한다.

### 추천 일정

28. 멤버로서, 여행지·기간·취향을 입력해 날짜별 추천 일정을 받고 싶다, 그래야 계획을 빨리 시작할 수 있다.
29. 멤버로서, 추천 일정의 각 장소가 실제로 있는지 서버가 검증해 주길 원한다, 그래야 없는 가게를 일정에 넣지 않는다.
30. 멤버로서, 검증에 실패한 추천 일정이 "확인 필요"로 표시되길 원한다.
31. 멤버로서, 추천 일정 중 고른 것만 플래너에 추가하고 싶다, 그래야 기존 계획이 덮어써지지 않는다.
32. 멤버로서, 채택한 추천 일정이 일반 일정 항목과 똑같이 다뤄지길 원한다.
33. 멤버로서, 같은 입력으로 다시 요청하면 저장된 결과를 즉시 받고 싶다.
34. 멤버로서, 여행의 하루 추천 횟수(10회)를 넘기면 언제 다시 가능한지 안내받고 싶다.
35. 멤버로서, Gemini가 실패하거나 형식이 깨진 응답을 주면 명확한 오류를 받고 싶다, 그래야 직접 일정을 쓸 수 있다.

### 앨범

36. 멤버로서, 촬영 시각과, 앱이 찾아 준 장소(있으면)를 함께 사진을 올리고 싶다.
37. 멤버로서, 앱이 찾아 준 장소가 이 여행의 장소인지 서버가 확인해 주길 원한다.
38. 멤버로서, 장소가 없는 사진은 촬영 날짜에만 연결되길 원한다.
39. 멤버로서, 사진의 장소 연결을 바꾸거나 해제하고, 일정에 없던 곳은 장소를 검색해 직접 연결하고 싶다.
40. 멤버로서, 날짜별·장소별·올린 사람별로 사진을 보고 싶다.
41. 멤버로서, 내가 올린 사진을 지우고 싶다.
42. 총무로서, 누가 올린 사진이든 지우고 싶다.
43. 멤버로서, 여행 사진이 200장을 넘으면 업로드가 거절되고 이유를 듣고 싶다.
44. 멤버로서, 허용되지 않는 파일 형식이나 너무 큰 파일은 거절되길 원한다.
45. 다른 여행의 사용자로서, 이 여행의 사진 주소를 알아도 볼 수 없어야 한다.

### 들른 곳

46. 멤버로서, 사진이나 지출이 연결된 장소가 "들른 곳"으로 구분되길 원한다, 그래야 계획만 한 곳과 실제로 간 곳을 나눠 볼 수 있다.
47. 멤버로서, 들른 곳이 언제(어느 날) 들른 곳인지 사진 촬영 시각과 지출 결제 시각으로 알고 싶다.
48. 멤버로서, 특정 멤버가 사진을 올리거나 결제한 곳만 보고 싶다.
49. 팀원으로서, 서버 DB와 저장소 어디에도 멤버의 위치 좌표가 남지 않길 원한다, 그래야 위치정보 수집 부담이 없다.
50. 멤버로서, 사진의 장소 연결을 해제하거나 사진을 지우면 그 장소가 더는 들른 곳으로 표시되지 않길 원한다(지출 연결이 남아 있지 않다면).
51. 멤버로서, 업로드된 사진 파일에 촬영 위치 정보가 남아 있지 않길 원한다.

### 지출

52. 총무로서, 영수증 사진을 올려 지출 초안을 받고 싶다(상호, 품목, 수량, 품목 금액, 총액).
53. 총무로서, 읽지 못한 값은 비워진 채로 받고 싶다, 그래야 원본을 보고 채울 수 있다.
54. 총무로서, 같은 영수증을 다시 올리면 저장된 분석 결과를 받고 싶다.
55. 총무로서, 영수증 없이 지출을 직접 입력하고 싶다.
56. 총무로서, 결제자로 아무 멤버나 지정하고 싶다.
57. 총무로서, 지출의 기본 분담 대상을 정하면 모든 품목에 적용되길 원한다(기본값은 전원).
58. 총무로서, 품목별로 분담 대상을 예외 수정하고 싶다.
59. 총무로서, 품목을 추가·수정·삭제하고 싶다, 그래야 할인이나 부분 환불을 품목 금액으로 반영할 수 있다.
60. 총무로서, 지출을 확정하려 할 때 어떤 확정 조건이 깨졌는지 목록으로 받고 싶다.
61. 총무로서, 확정 조건이 모두 맞으면 지출이 정산에 반영되길 원한다.
62. 총무로서, 확정 조건을 무시하고 강제로 확정할 수 없어야 한다.
63. 총무로서, 영수증 상호로 검색한 장소 후보 중 하나를 골라 지출에 붙이고 싶다.
64. 총무로서, 지출의 장소를 비워 두고 싶다.
65. 총무로서, 확정된 지출도 고치거나 지우고 싶다, 그래야 뒤늦게 발견한 오류를 바로잡을 수 있다.
66. 총무로서, 네트워크 재시도 때문에 같은 지출이 두 번 생기지 않길 원한다.
67. 일반 멤버로서, 지출을 볼 수는 있지만 만들거나 고칠 수는 없어야 한다.
68. 멤버로서, 지출의 영수증 원본을 보고 싶다, 그래야 금액을 믿을 수 있다.

### 정산과 송금

69. 멤버로서, 여행 전체의 내 결제액·부담액·잔액을 보고 싶다.
70. 멤버로서, 송금 제안("준호 → 민지 8,500원")을 보고 싶다.
71. 멤버로서, 내 부담액이 어느 지출의 어느 품목에서 왔는지 근거를 보고 싶다.
72. 멤버로서, 균등 분담에서 남는 원이 정해진 순서(가입 순서)대로 배분되길 원한다, 그래야 계산이 매번 같다.
73. 멤버로서, 확정되지 않은 지출은 잔액에 들어가지 않길 원한다.
74. 총무로서, 송금 제안 그대로 송금을 기록하고 싶다.
75. 총무로서, 일부 금액만 송금된 경우 금액을 직접 기록하고 싶다.
76. 총무로서, 잘못 기록한 송금을 지우고 싶다.
77. 멤버로서, 송금 기록 후 지출이 바뀌면 잔액과 송금 제안이 자동으로 다시 계산되길 원한다(재정산).
78. 멤버로서, 모든 멤버의 잔액이 0이면 정산이 끝났다는 것을 알고 싶다.
79. 일반 멤버로서, 송금을 기록하거나 지울 수 없어야 한다.

### 지도

80. 멤버로서, 여행의 모든 장소와 각 장소에 묶인 일정 항목·사진·지출을 한 번에 받고 싶다, 그래야 지도 핀을 그릴 수 있다.
81. 멤버로서, 날짜를 골라 그날 계획했거나 들른 장소만 받고 싶다.

### 권한 전반

82. 비로그인 사용자로서, 어떤 여행 데이터도 받을 수 없어야 한다.
83. 다른 여행의 사용자로서, 이 여행의 어떤 데이터도 읽거나 쓸 수 없어야 한다.
84. 팀원으로서, Gemini·카카오 API 키와 Supabase 서비스 키가 앱에 절대 노출되지 않길 원한다.

## Implementation Decisions

### 구조

- 서버는 Python FastAPI로 만들고 Render에 배포한다. 데이터는 Supabase PostgreSQL, 이미지는 Supabase Storage 비공개 버킷, 인증은 Supabase Auth를 쓴다.
- 앱은 DB·Storage에 직접 접근하지 않는다(ADR-0002). 서버만 서비스 키를 가지며, 클라이언트에 대한 RLS 정책은 전부 거부로 둔다.
- 외부 의존성은 각각 하나의 어댑터 뒤에 둔다. 서버의 나머지 코드는 어댑터 인터페이스만 안다.
  - **인증 검증기**: 로그인 토큰 → 사용자 id. 실패 시 401.
  - **Gemini 클라이언트**: (여행지, 기간, 취향) → 날짜별 추천 일정 JSON / 영수증 이미지 → 지출 초안 JSON.
  - **장소 검색기**: (키워드, 선택적 좌표) → 카카오 장소 후보 목록(카카오 장소 id, 이름, 주소, 좌표).
  - **객체 저장소**: 업로드, 삭제, 짧은 만료의 서명 URL 발급.
- 정산 계산은 DB도 HTTP도 모르는 순수 계산 모듈로 분리한다. 입력은 멤버 목록(가입 순서 포함), 확정된 지출(결제자, 품목, 품목별 분담 대상), 송금 목록이고, 출력은 멤버별 결제액·부담액·잔액, 송금 제안 목록, 멤버별 품목별 부담 근거다.
- 권한 판정은 한 모듈에서 한다: "이 사용자가 이 여행의 멤버인가", "총무인가", "이 사진/일정 항목의 주인인가". 모든 엔드포인트가 이 모듈을 거친다.

### 데이터 모델(테이블과 핵심 제약)

- **사용자 프로필**: Supabase Auth 사용자 id, 표시 이름.
- **여행**: 이름, 시작일, 종료일(시작일 ≤ 종료일), 총무 멤버, 현재 초대 코드.
- **멤버**: 여행, 사용자, 가입 순서. (여행, 사용자) 유일. 여행당 최대 10명.
- **초대 코드**: 8자리, 0/O/1/I 제외 문자 집합, 전역 유일. 재발급하면 이전 코드는 무효.
- **장소**: 여행, 카카오 장소 id, 이름, 주소, 좌표. (여행, 카카오 장소 id) 유일. 카카오 검증을 통과하지 않은 장소는 만들지 않는다.
- **일정 항목**: 여행, 날짜(여행 기간 안), 하루 안의 순서, 시간(선택), 장소(선택), 메모, 예상 비용(선택, 원), 만든 멤버.
- **추천 요청**: 여행, 입력 해시, 요청 시각, 결과(추천 일정 목록과 각 항목의 검증 결과). 입력 해시가 같으면 결과를 재사용한다. 여행별 하루 10회 제한은 이 테이블로 센다.
- **사진**: 여행, 올린 멤버, 저장소 키, 촬영 시각, 연결된 장소(선택), 연결 방식(자동/수동). 촬영 위치 좌표는 저장하지 않는다. 여행당 200장.
- **지출**: 여행, 결제자 멤버, 상태(draft / needs_review / confirmed), 총액, 결제 시각, 상호(선택), 장소(선택), 영수증(선택), 기본 분담 대상, 멱등 키.
- **품목**: 지출, 이름, 수량(표시용), 금액(원 단위 정수).
- **품목 분담 대상**: 품목, 멤버.
- **영수증**: 여행, 저장소 키, 이미지 해시, 분석 결과. 같은 이미지 해시는 분석 결과를 재사용한다.
- **송금**: 여행, 보낸 멤버, 받은 멤버, 금액(양의 정수), 기록 시각.
- 지출과 품목·분담 대상은 한 트랜잭션으로 저장한다.

### 규칙

- **여행 기간 변경**: 총무만. 줄어든 기간 밖에 일정 항목이 있으면 409와 해당 날짜 목록. 사진은 촬영 시각 기준이라 영향받지 않는다.
- **멤버 나가기/내보내기**: 결제자 또는 분담 대상으로 한 번이라도 지정된 멤버는 409. 총무 본인은 나갈 수 없다. 나간 멤버의 사진은 삭제한다.
- **여행 삭제**: 총무만. 저장소의 사진·영수증 파일까지 삭제한다.
- **추천 일정 흐름**: Gemini에 출력 JSON 형식을 지정한다(날짜, 순서, 장소명, 지역, 예상 체류 시간, 한 줄 설명). 형식 검증이 실패하면 1회 재요청하고, 그래도 실패하면 502. 각 장소는 "장소명 + 지역"으로 장소 검색기에 질의하고, 이름이 충분히 일치하는 첫 후보를 채택한다. 일치하지 않으면 "확인 필요"로 표시하고 장소를 비운다. 채택 요청은 고른 추천 일정 id 목록을 받아 일정 항목으로 만들고, 장소는 (여행, 카카오 장소 id) 기준으로 재사용한다.
- **사진 자동 연결**: 앱이 휴대폰 안에서 촬영 위치로 같은 날 일정 항목의 장소 중 300m 안의 가장 가까운 곳을 찾아, 장소 id만 연결 방식 "자동"으로 보낸다. 서버는 그 장소가 이 여행의 장소인지만 확인한다. 장소가 없으면 촬영 날짜로만 분류한다. 사용자가 수동으로 바꾼 연결은 그대로 둔다.
- **사진 수동 연결**: 일정에 없던 곳은 사용자가 장소를 검색해 연결하며, 이때 그 장소가 여행의 장소로 새로 생긴다.
- **사진 업로드**: 앱이 압축(긴 변 1600px, JPEG)하면서 EXIF를 모두 제거하고, 촬영 시각과 (있으면) 장소 id만 메타데이터로 보낸다. 서버는 형식(JPEG)과 크기 상한을 검사한다. 서버 API는 어떤 경우에도 사람의 위치 좌표를 받지 않는다.
- **들른 곳**: 사진 또는 지출이 연결된 장소다. 들른 날짜는 연결된 사진의 촬영 시각과 지출의 결제 시각에서 나온다. 저장하지 않고 조회 시 계산한다.
- **지출 확정 조건**: (1) 품목 금액 합 = 총액, (2) 모든 품목에 분담 대상 1명 이상, (3) 결제자 지정, (4) 모든 금액이 0보다 큰 원 단위 정수. 확정 요청에서 조건이 깨지면 상태를 needs_review로 바꾸고, 깨진 조건 목록과 함께 422를 돌려준다. 강제 확정은 없다.
- **영수증 분석**: 결과는 항상 draft 상태의 지출 초안이다. 읽지 못한 값은 null로 둔다. 분석이 실패해도 영수증은 저장하고 빈 지출 초안을 만든다(수동 입력으로 이어감).
- **지출 장소 후보**: 영수증 상호(또는 총무가 입력한 검색어)로 카카오를 검색해 후보를 돌려준다. 이 여행에 이미 있는 장소와 일치하는 후보를 앞에 둔다. 자동으로 붙이지 않는다.
- **멱등성**: 지출 생성과 영수증 업로드는 멱등 키를 받아, 같은 키의 재요청에는 처음 결과를 돌려준다.
- **정산 계산**: 원 단위 정수로 계산한다. 품목 금액을 분담 대상 수로 나눈 몫을 모두에게 주고, 나머지는 분담 대상을 가입 순서로 정렬해 앞에서부터 1원씩 준다. 잔액 = 결제액 − 부담액 + 보낸 송금액 − 받은 송금액. 송금 제안은 받을 사람(양수)과 보낼 사람(음수)을 큰 금액부터 짝짓는 탐욕 방식으로 만든다. 같은 입력이면 항상 같은 출력이 나와야 한다(동률은 가입 순서로 정한다). 최소 송금 횟수는 보장하지 않는다.
- **송금 기록**: 총무만. 금액은 양의 정수. 송금 제안과 일치할 필요는 없다.
- **지도 데이터**: 여행(선택적으로 날짜, 멤버)에 대해 장소 목록을 돌려준다. 각 장소에는 들른 곳 여부, 들른 날짜, 묶인 일정 항목·사진(썸네일 서명 URL)·지출 요약이 들어 있다. 멤버 필터는 그 멤버가 사진을 올렸거나 결제한 장소로 거른다.

### API 형태

- 모든 경로는 여행 아래에 둔다(여행 목록, 여행 생성, 초대 코드로 가입 제외). 자원별로 생성·조회·수정·삭제를 둔다: 여행, 멤버, 초대 코드, 장소 검색, 일정 항목, 추천 요청과 채택, 사진, 영수증, 지출(확정 동작 포함), 장소 후보, 정산 결과, 송금, 지도.
- 오류는 공통 형식(코드, 사람이 읽을 메시지, 선택적 세부 목록)으로 돌려준다. 401 미인증, 403 권한 없음, 404 없음(다른 여행의 자원도 존재를 드러내지 않도록 404), 409 규칙 충돌, 422 검증 실패, 429 추천 한도 초과, 502 외부 API 실패.
- 금액은 모두 원 단위 정수, 날짜는 ISO 날짜, 시각은 시간대를 포함한 ISO 시각으로 주고받는다.
- 이미지 응답은 파일이 아니라 짧은 만료의 서명 URL이다.

### 기술 스택 보강 (2026-10-28)

- **DB 접근**: SQLAlchemy 2로 DB에 접근하고, 스키마 변경은 Alembic 마이그레이션으로만 한다. 테스트 DB와 Supabase 운영 DB는 같은 마이그레이션으로 만든다.
- **Gemini 응답 형식**: google-genai의 응답 스키마 지정 기능에 Pydantic 모델을 넘겨 추천 일정·지출 초안의 JSON 형태를 강제한다. 서버의 형식 검증과 1회 재요청 규칙은 그대로 둔다.
- **API 명세**: FastAPI가 만드는 OpenAPI 명세가 앱과의 계약이다. 요청·응답은 모두 Pydantic 모델로 선언해 명세에 빠짐없이 드러나게 한다.

## Testing Decisions

- 좋은 테스트는 외부에서 보이는 동작만 검증한다. HTTP 요청을 보내고 응답과 그 뒤의 조회 결과를 확인한다. 내부 함수 호출 순서, 어떤 SQL이 실행되었는지, 어댑터가 몇 번 불렸는지는 검증하지 않는다. 단, 추천 재사용과 영수증 결과 재사용처럼 "다시 부르지 않는다"가 요구사항 그 자체인 경우는 가짜 어댑터의 호출 기록으로 확인한다.
- **경계 1 — HTTP API(주 경계)**: FastAPI 테스트 클라이언트로 실제 엔드포인트를 호출한다. DB는 테스트용 PostgreSQL을 실제로 띄워 쓴다(트랜잭션·유일 제약 동작 때문에 SQLite로 대신하지 않는다). 인증 검증기, Gemini 클라이언트, 장소 검색기, 객체 저장소는 테스트용 가짜로 바꾼다. 이 경계로 검증하는 것:
  - 권한: 비로그인, 다른 여행 사용자, 일반 멤버의 지출·송금 변경 차단, 남의 사진 삭제 차단
  - 초대 코드 가입, 재발급 후 이전 코드 무효, 10명 제한
  - 여행 기간 축소 거절, 멤버 나가기 제한, 여행 삭제
  - 일정 항목 CRUD, 같은 카카오 장소 재사용
  - 추천 일정: 검증 성공/실패 표시, 채택, 같은 입력 재사용, 하루 10회 제한, Gemini 형식 오류
  - 사진 연결: 다른 여행의 장소 id 거절, 수동 연결로 새 장소 생성, 200장 제한
  - 들른 곳: 사진·지출 연결 여부와 날짜·멤버 필터에 따른 지도 데이터
  - 위치 좌표 비수집: 사진 업로드 API가 좌표 필드를 받지 않고, 저장된 사진 파일에 EXIF가 없다
  - 지출 확정 조건 각각, 멱등 키, 확정 후 수정·삭제
  - 송금 기록 후 지출 변경 시 재정산 결과
- **테스트 DB 준비**: 테스트는 환경 변수로 받은 PostgreSQL 연결 주소를 쓴다. Docker로 띄우든 Windows에 직접 설치하든 상관없다. 테스트 시작 시 Alembic 마이그레이션으로 스키마를 만든다.
- **경계 2 — 정산 계산 모듈(보조 경계)**: 순수 계산이므로 입력 → 출력 표 형태의 사례 테스트로 검증한다. 필수 사례: 기획서 대표 사례(간식 12,000/3명, 음료 9,000/2명, 케이블 9,000/1명 → 민지 13,000, 준호·수빈 각 8,500), 나머지 원 배분(10,000원을 3명 → 가입 순서 앞의 1명이 3,334), 복수 결제자, 일부 송금 후 지출 삭제로 잔액 부호가 바뀌는 경우, 모든 잔액 0, 결정성(같은 입력을 두 번 넣어도 같은 송금 제안).
- **선행 사례**: 저장소에 백엔드 코드와 테스트가 아직 없다. 이 스펙이 첫 테스트 구성(pytest, 테스트 DB 준비, 가짜 어댑터 주입 방식)을 만든다.

## Out of Scope

- 앱 화면 전체(프론트엔드 스펙에서 다룸)
- 실시간 동기화(웹소켓 등), 플래너 실시간 공동 편집. 플래너는 마지막 저장이 반영된다.
- GPS 이동경로 기록, 친구 현재 위치 공유, 사람의 위치 좌표 수집·저장 전반(ADR-0003)
- 앨범의 영상, 댓글, 좋아요
- 직접 금액 분담, 수량 비례 분담, 할인 자동 배분
- 실제 은행 송금, 계좌 연동, 복수 통화
- 소셜 로그인, 총무 위임·공동 총무
- 자체 학습 모델(지출 유형 분류 등)
- 여행 "종료" 상태
